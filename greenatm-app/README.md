# Green ATM Tracker — แอป Next.js + SQLite

ระบบติดตามความพร้อมด้านสิ่งแวดล้อมตาม **แบบประเมินภายใน วว.นบ209_2569-14**
(4 หมวด · 24 รายการ · Level 0–5 ต่อรายการ) พร้อมชั้นเชื่อมต่อโมเดลสำหรับงาน agent

**สถานะ: 6 หน้าจอ + ฐานข้อมูลจริง + สิทธิ์ 3 บทบาทที่บังคับฝั่ง server ใช้งานได้แล้ว**
ส่วน agent (`agentLoop.ts`) เขียนไว้แล้วแต่ **ยังไม่เคยรันกับ endpoint จริง** — ดูหัวข้อ “ยังไม่ได้ทดสอบ”

---

## เริ่มใช้งาน

```bash
npm install
npm run build
npm start                      # แล้วเปิด http://localhost:3000
```

ฐานข้อมูล SQLite สร้างเองอัตโนมัติที่ `data/greenatm.sqlite` ตอนเปิดครั้งแรก
(ใช้ `node:sqlite` ที่มาพร้อม Node 22 — **ไม่ต้อง compile native module**)

ล้างข้อมูลกลับไปเป็นชุดตั้งต้น: `npm run db:reset` (ต้องปิดเซิร์ฟเวอร์ก่อน ไม่งั้นไฟล์ถูกล็อก)

ถ้าจะต่อโมเดล ให้เพิ่ม `.env.local` ด้วย:

```bash
cp .env.example .env.local     # Windows: copy .env.example .env.local
npm run check:llm              # ตรวจจากบรรทัดคำสั่ง ไม่ต้องเปิดเว็บ
```

**รันจากเครื่องที่จะรัน backend จริงเท่านั้น** — endpoint เป็น IP ภายใน
เครื่องอื่นในเครือข่ายอื่นจะได้ผลที่ไม่มีความหมาย

## กฎสำคัญที่บังคับไว้ในฐานข้อมูล ไม่ใช่แค่ในโค้ด

| กฎ | บังคับที่ไหน |
|---|---|
| **`audit_log.actor` ห้ามเป็น `ai`** | `CHECK (actor <> 'ai')` ใน schema + guard ใน `queries.ts` |
| ชั้นหลักฐานที่ยืนยันแล้วต้องมีคนยืนยัน | `CHECK ((confirmed_tier IS NULL) = (confirmed_by IS NULL))` |
| เป้าต้องไม่ต่ำกว่าระดับที่ได้แล้ว | `CHECK (target_level >= achieved_level)` |
| agent เขียนได้แค่ตาราง `pending_progress` | ไม่มีเส้นทางใดให้ `ai` เขียน `tracked_item` |
| ค่าความคืบหน้าจริงเปลี่ยนที่จุดเดียว | `confirmPending()` — เรียกจาก `POST /api/pending/[id]` เท่านั้น |
| ระดับ 0 = “ยังไม่ถึงระดับ 1” เป็นค่าที่ถูกต้อง | `CHECK (achieved_level BETWEEN 0 AND 5)` — ข้อ 1.2 ใช้สถานะนี้จริง |

### สองตัวเลขที่ระบบไม่ยอมรวมกัน

`progress_percent` (เจ้าของกรอก) กับ `verified` (คนยืนยันหลักฐาน A/B แล้ว) เก็บและคำนวณแยกกัน
**ตัวเลขซ้ายดันตัวเลขขวาไม่ได้เลย** — ทดสอบไว้ว่ากดยืนยันความคืบหน้าแล้ว Verified ไม่ขยับ

## ค่าที่ต้องเติมใน `.env.local`

| ตัวแปร | หมายเหตุ |
|---|---|
| `LLM_PROVIDER` | `qwen` หรือ `dgx` — **ไม่ใช่แค่ชื่อ** แต่ละตัวมี option ของตัวเองใน `src/lib/llm/providers.ts` |
| `LLM_BASE_URL` | ต้องลงท้าย `/v1` · โค้ดต่อ `/chat/completions` ให้เอง |
| `LLM_MODEL` | ชื่อรุ่นที่ served **จริง** — ยืนยันจาก `/v1/models` หรือจาก facilitator |
| `LLM_API_KEY` | จาก facilitator · ใส่บนเครื่องเท่านั้น **ห้ามพิมพ์ลงแชท สกรีนช็อต หรือ commit** |
| `LLM_TIMEOUT_MS` | ค่าเริ่มต้น 120000 — เป็นค่าตั้งต้น ไม่ใช่ค่าที่วัดมาจาก endpoint |
| `ALLOW_INSECURE_LLM_HTTP` | ดูหัวข้อถัดไป |

### ประตูกันพลาดเรื่อง HTTP

`QWEN-FPT-INTEGRATION.md` เขียนไว้ว่า *ต้องได้ HTTPS endpoint หรือเส้นทางภายในที่อนุมัติแล้ว
ก่อนส่ง key จริงหรือข้อมูลที่ไม่เปิดเผย* แต่ endpoint ที่บันทึกไว้เป็น `http://` ธรรมดา

โค้ดจึง **ปฏิเสธที่จะส่ง key ข้าม `http://`** และขึ้น configuration error ที่อ่านรู้เรื่องแทน
มีสามทางออก เลือกตามสถานการณ์จริง:

1. ขอ **HTTPS endpoint หรือเส้นทางภายใน** จาก facilitator แล้วใส่ใน `LLM_BASE_URL` ← ทางที่ถูก
2. ถ้า endpoint **ไม่ต้องใช้ key** เลย ปล่อย `LLM_API_KEY` ว่างไว้ → ทดสอบได้ทันที ไม่ติดประตูนี้
3. ถ้า facilitator ยืนยันแล้วว่าเป็นเส้นทางภายในที่ปลอดภัย ตั้ง `ALLOW_INSECURE_LLM_HTTP=true`
   — เป็นการตัดสินใจที่ต้องตั้งใจทำ ไม่ใช่สิ่งที่หลุดไปเอง

> **ทางหลักของทีมคือ DGX Spark** — ถ้ายังไม่ได้ HTTPS ของ Qwen ให้ตั้ง `LLM_PROVIDER=dgx`
> แล้วทดสอบ DGX ก่อน อย่าเสียเวลารอ

| สิ่งที่ยังไม่ได้พิสูจน์ | สถานะจริง |
|---|---|
| **`agentLoop.ts` (279 บรรทัด)** | เขียนครบแล้ว แต่**ยังไม่เคยรันกับ endpoint จริงแม้แต่ครั้งเดียว** |
| **`POST /api/llm/tf6`** | ยังไม่ได้ยิง — DGX `10.0.63.215` ติดต่อไม่ได้จากเครื่องที่พัฒนา (คนละ subnet) |
| **คอลัมน์ Suggestion** | มาจาก**กฎในโค้ด ไม่ใช่โมเดล** — ห้ามเรียกว่า AI บนสไลด์จนกว่าจะเปลี่ยน |
| **แจ้งเตือน** | ร่างลง Outbox เท่านั้น **ไม่มี SMTP / LINE / Teams credential ในโปรเจกต์** จึงส่งจริงไม่ได้ |
| **หน้าแชตผู้ช่วยรายกอง (M6′)** | ยังไม่ได้ทำ — ฟอร์มในหน้ารายละเอียดเป็นทางที่ใช้อยู่ |

และทีมกลางยังยืนยันชั้นหลักฐานด้วยมือได้ — ไม่มีหน้าไหนค้างเพราะโมเดลล่ม

## กฎที่บังคับไว้ในโค้ด ไม่ใช่เขียนไว้เฉย ๆ

| กฎ | อยู่ที่ไหน |
|---|---|
| placeholder ที่ยังไม่ถูกแทน = configuration error ที่อ่านรู้เรื่อง ไม่ใช่ยิงแล้วพัง | `config.ts` |
| key ไม่ถูก log ไม่ถูกส่งกลับ client — หน้าเว็บเรียกได้แค่ API route ของตัวเอง | `config.ts` · `describeConfig()` |
| ปฏิเสธส่ง key ข้าม `http://` เว้นแต่ประกาศยอมรับไว้ชัดเจน | `config.ts` |
| **ล้มเหลวคือล้มเหลว** — ไม่มีคำตอบสำเร็จรูปแทนคำตอบที่ยิงไม่สำเร็จ | `client.ts` |
| **content ว่าง = ยังไม่สำเร็จ** ต้องรายงาน `finish_reason` ตามจริง | `client.ts` |
| ถ้า HTTP 400 เพราะ `chat_template_kwargs` → retry ครั้งเดียวโดยถอดออก แล้วบอกว่ารอบไหนผ่าน | `client.ts` |
| **validate argument ทุกครั้งก่อน execute** ไม่เชื่อสิ่งที่โมเดลส่งมา | `tools.ts` |
| ไม่มีข้อมูลในระบบ → ตอบว่าไม่มี **ห้ามแต่งตัวเลขหรือชื่อ** | `tools.ts` |
| JSON ผิดรูป 2 ครั้งติด → หยุด บันทึกว่าไม่สำเร็จ (PLAN §5.3) | `agentLoop.ts` |
| ชนเพดาน tool call → รายงานว่าไม่สำเร็จ **ไม่เดาให้จบ** | `agentLoop.ts` |

## TF6 — และทำไมมันตัดสินเรื่อง agent ของทั้งทีม

เอกสาร integration ทั้งสองฉบับเขียนตรงกันว่า *อย่าสรุปว่า tool calling ใช้ได้เพียงเพราะแชทธรรมดาใช้ได้*
และ *prompt ที่พูดถึง tool ไม่ใช่การเรียก tool* — `POST /api/llm/tf6` จึงทดสอบของจริง:

```
ทางหลัก   ส่ง tools[] → endpoint คืน tool_calls → validate argument → execute → ป้อนผลกลับ → สรุป
ทางสำรอง  ถ้าไม่คืน tool_calls → ลูปเลือก action ด้วย JSON ที่ validate ด้วย schema ในโค้ด
```

ทางสำรอง **ยังเป็น agent ตามนิยาม** (โมเดลเลือกการกระทำจากผลที่สังเกตได้ ภายใต้ขอบเขตที่บังคับ)
แต่ **ถ้าใช้ทางสำรอง ต้องเขียนบนสไลด์ตามจริง ห้ามอ้างว่าใช้ native tool calling**

หน้า `/llm-check` แสดงลำดับที่เกิดขึ้นจริงทีละขั้น — ใช้เป็นหลักฐานบนเวทีได้เลย
